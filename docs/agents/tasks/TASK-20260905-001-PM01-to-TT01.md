## Architecture review (verbatim source)

### A) Good to Great (as-is)

1. **[High impact / low risk] Main-process security boundary is directionally correct.**  
   Renderer access is mediated through `contextBridge`; `nodeIntegration: false`, `contextIsolation: true`, and `sandbox: true` are enabled in `src/main.ts:53-65`. Private Epic keys remain in main-process vault code (`src/ipc/secure-vault.ts:60-70`), while the renderer receives only public configuration.
2. **[High / low] Domain-oriented services exist.**  
   Patient, nurse, layout, assignment, facility, spectra, and FHIR concerns are separated under `renderer/src/services`. Clinical transformations are also isolated in helpers such as `renderer/src/lib/fhir-apply-census.ts`.
3. **[Medium / low] FHIR mapping is testable and mostly decoupled.**  
   `src/fhir/mapper.ts`, `src/fhir/epic-client.ts`, and their tests provide a reasonable pure-data boundary. `applyCensusToRooms` is independently testable.
4. **[Medium / low] Audit and security primitives are centralized.**  
   Audit record creation/redaction is centralized in `src/security/audit.ts`; cryptography and password policy have dedicated modules and tests.

### B) Needs Attention (broken)

1. **[Critical / medium] Persistence architecture contradicts the product model.**  
   Advertises SQLite/better-sqlite3 (`README.md:18`, `README.md:117-121`) but active implementation is renderer-side JSON via localStorage or encrypted whole-document storage (`renderer/src/lib/database-simple.ts:22-110`). No SQLite dependency in root package.json. Storage, transactionality, concurrency, migration, and failure semantics differ.
2. **[High / medium] Two database implementations remain.**  
   `database-auth.ts` and `database-simple.ts` both define `SimpleDatabase`; former excluded by `renderer/tsconfig.json:37` but still in repo with older schema.
3. **[High / medium] Runtime/type-check boundaries inconsistent.**  
   `renderer/tsconfig.json:34-62` excludes many root-level components, yet `components/unit-view-client.tsx` imports those root-level files (`:5-24`).
4. **[High / medium] Error handling converts data failures into empty/seeded state.**  
   `patientService.getPatients` seeds or returns `[]` after any failure (`patientService.ts:13-33`). Several services catch/log/return fallbacks (`layoutService.ts:44-107`). Outages look like empty units.
5. **[High / medium] Whole-database writes are async and non-serialized.**  
   `database-simple.ts:164-178` calls `window.electronAPI.saveSecureStore` without awaiting. Every mutation `JSON.stringify`s the full DB through IPC. Rapid edits can reorder/lose updates.
6. **[Medium / medium] FHIR sync is N+1.**  
   `src/fhir/epic-client.ts:200-214` loops encounters with up to four searches per patient plus fallbacks. No batching, bounded concurrency, or cache.
7. **[Medium / low] Census apply is quadratic.**  
   `fhir-apply-census.ts:64-129` repeatedly scans/splices remaining census.
8. **[Medium / low] Duplicated init paths.**  
   `App.tsx` and `App-auth.tsx` both init DB and auth.
9. **[Medium / low] Docs/metadata stale.**  
   Version 5.1.5-c vs README/changelog 5.0.1; `npm start` missing from scripts.

### C) Reorganization Candidates

1. One authoritative storage boundary (main-process repository/IPC → SQLite or one documented encrypted store)
2. Collapse duplicate component trees (`renderer/src/*.tsx` vs `components/`)
3. Remove/quarantine obsolete abstractions (`database-auth.ts`, `App-auth.tsx`, backups, debug files)
4. Consolidate UI primitives (`ui/` vs `components/ui/`)
5. Split `UnitViewClient` by responsibility

### D) Better if

1. Per-mutation whole-store persist → queued transactional writes
2. Service fallback swallowing → typed error/result propagation
3. Direct component `getDb()` → service/repository commands
4. FHIR sequential enrichment → batched/bounded concurrent fetch
5. Repeated metadata lookup → one unit snapshot
6. Deep `JSON.stringify` compare → revision/dirty tracking
7. `window.location.href = '/'` → in-memory unit transitions
8. Linear census matching → indexed maps
9. Untyped `action_history` → discriminated types or remove unused path

**Overall assessment (source):** strongest design is main-process security/FHIR boundary. Largest problem is renderer-owned mutable whole-database JSON vs documented database-backed Electron app. Residue from prior sweeps: duplicate trees, duplicate DBs, backups, excluded production-looking files, multiple init paths.
